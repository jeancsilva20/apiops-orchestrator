# Design — add-sen-completeness

*(pt-BR. Keywords SHALL/MUST em inglês. Complementa o proposal e a spec `sen-completeness`.)*

## Context

- A feature selada do `sen completeness` (`docs/feat-command-sen-completeness/`) definiu o AG (`adaptive-governance`) como fonte primária. As sondas posteriores (`problemas.md`, 24/09) provaram que o AG só mantém report da **última revisão**; nem a UI do Manager expõe histórico de completude por revisão via AG.
- O endpoint do Manager `GET /api-manager/api/v3/revisions/{rid}/completeness` (swagger `swagger-apim-v4/swagger.json`, `CompletenessBean`) aceita **o id da revisão no path** e respondia 200 ao vivo nas mesmas sondas — cobrindo qualquer revisão.
- A spec selada original **não é alterada** (fica como registro histórico/planejamento); esta change estabelece o desvio deliberado e a ADR 0008 receberá nota de supersedência parcial.
- Estado do código: não há implementação do `sen completeness` (nenhum arquivo de comando/port/service dedicado). A infra do `sen list` já fornece o `ManagerApiAdapter` com `_request` traduzindo transporte → sinais tipados do port, e `HttpClient` com retries/timeout/RFC 7807 (padrões §7); `get_revision_completeness` é NOVO nesta fatia.

## Goals / Non-Goals

**Goals:**
- Entregar `sen completeness` funcional para **qualquer revisão** do histórico, com gramática A1–A7 da feature preservada (`--api-id` e `--revision` obrigatórios, `--score-only`, `-o`, `-v`).
- Contrato JSON versionado `apiops.sen-completeness/v1` **rebocado** ao que o Manager efetivamente entrega (`completenessScore`, `suggestions[]`) — sem campos-fantasma.
- Simplificar o plano de chamadas: 1 GET do Manager + satélite api-finder degradável (contexto/posse).
- Visualização TEXT coerente com o dado disponível: barra/gate + lista integral de `Suggestions` (sem severidade/impacto fabricados client-side).

**Non-Goals:**
- Avaliação local de completude (`sen validate`, fase 2) — apenas garantir reuso do `CompletenessService`.
- Histórico de maturidade estruturado por revisão (depende da Plataforma — P-f permanece aberto para o AG; caso venha, a fonte pode ser reavaliada numa change futura).
- Gate dinâmico via `workflows/{id}/stages` (P-a permanece postergado; gate 70% hardcoded `p10.v1` se mantém na V1).
- Alterar a spec/feature docs originais ou o ADR 0008 além da nota de supersedência.

## Decisions

**D1 — Fonte única: Manager `GET /revisions/{rid}/completeness`.** O path já carrega a revisão pedida, matando o bloqueio do AG. Alternativa (manter AG + aceitar "só última revisão") rejeitada porque invalida a semântica de A3 (`--revision` obrigatório) e derruba o valor do comando a um espelho de uma única revisão. Route/verb/documento confirmados no swagger (`CompletenessBean`).

**D2 — Contrato v1 rebalanceado (subtração assumida).** Campos derivados de violação estruturada do AG são **removidos** da árvore (`violations[]`, `rulesLost[]`, `issues.bySeverity`, `severity`, `impactPoints`, `range`, `classification`, `agCatalogId`, `agId`, `last`): não há como prová-los sem alicerce de dado; nulls-fantasma rompem o princípio "dump honesto" (critério de aceite 4 da feature). Probe adicional (25/09) confirmou o wire real: `{completenessScore, suggestions[]}` — **a plataforma não classifica a partir do Manager**, logo a classificação B/I/A NÃO é derivada client-side (seria invenção de dado; ver Q4). O que permanece: `schema`, `generatedAt`, `api{managerId,name,version,context?}`, `revision{managerId}`, `maturity{score}`, `gate{percent}`, `suggestions[]{text,index}`. Posse (`type/groupName/owner`) mora dentro do bloco `api` — é dado da API; **nenhum bloco de estado-de-coleta existe no contrato** (sem status/source/note: degradação do lookup se expressa só pela ausência dos campos — regra da casa "dado ou nada", que também cortou o `source` do gate/original).

**D3 — Sugestões viram entidades de primeira classe com índice.** `suggestions[]` do Manager é `array[string]`; o model pydantic registra `{index, text}` (ordem do wire preservada = ordem de exibição — determinismo para automação). Alternativa (keyed-map) rejeitada: inventaria chave estável que o backend não garante.

**D4 — Sem port dedicada: a fronteira já existe (evolução do ADR 0008).** Com a fonte voltando a ser o próprio Manager (D1), a port dedicada `CompletenessPort` perdeu a razão de ser: Protocol de 1 método com 1 implementação eterna seria indireção speculative; a fronteira hexagonal real já é detida por `ManagerApiPort`/`ManagerApiAdapter`. A adaptam-se: novo método `get_revision_completeness(revision_id)` no adapter + assinatura correspondente na `ManagerApiPort`. Model e Service permanecem próprios (bloco reutilizável do `sen validate`). Alternativa (manter `CompletenessPort`) rejeitada: outro backend não é a fonte hoje — quando o AG historizar revisões (P-f), a abstração é extraída então (composition root facilita). **Regra de fronteira dura (não-negociável, aprendida do débito consciente do sen list/D3):** o dict cru do wire MORRE DENTRO do adapter — `ManagerApiAdapter.get_revision_completeness` devolve valor tipado de domínio (`CatalogRevisionCompleteness{score, suggestions[list[str]]}`, definido em `catalog_revision_model.py` — ver D9), nunca `Dict[str, Any]`; quem divide o par de falas wire↔domínio é o outbound, não o service (diferença de qualidade frente ao sen list: lá o dict cru atravessou service e chegou a atingir o CLI; aqui as fronteiras voltam a blindar).

**D4.b — Erros seguem a casa PADRONIZADA: módulo dedicado de exceptions por domínio.** A padronização do repo (25/09, pós-`type-api-catalog-frame`) instituiu `application/exceptions/<dominio>_exceptions.py` com erros TIPADOS de domínio — p.ex. `listing_exceptions.py` (`ApiNotFound(api_id)`, `InvalidWindow(argumento, regra)`), e a CLI traduz para exit/msg. Esta change segue o MESMO padrão: `application/exceptions/completeness_exceptions.py` com `CompletenessNotFound(revision_id)`, `CompletenessUnauthorized`, `CompletenessDenied`, `CompletenessPlatformError(detail)`, mapeados no CLI para `exit 2` + mensagem PT-BR por status (404 → orientar `sen list api --id X --revisions`; 401 → orientar `sen login`); RFC 7807 do `HttpErrorMapper` segue transportando a causa do adapter. Buckets: `exit 1` = guard pré-rede local do CLI (nem chega ao service); `exit 2` = refusais da plataforma; lookup de identidade caído NÃO é exceção (soft-fail interno). *(Revoga o desenho intermediário de exceção única `CompletenessError(message, exit_code)` espelhando `CliError` — a casa evoluiu para módulo dedicado tipado.)*

**D4.c — Projection vs. reuso: contratos versionados são subconjuntos, nunca inclusões.** O bloco `api` do contrato NÃO referencia os models de catálogo/publisher porque o DTO de saída é projeção mínima do que o contrato declara; com a exclusão do envelope (D9), a projeção da identidade é montada na application a partir da `ApiCatalogEntry` TIPADA. **Fundação REALIZADA e consolidada (25/09):** a change irmã `type-api-catalog-frame` foi implementada e ARCHIVADA — o frame do api-finder é tipado (`ApiCatalogEntry` em `api_catalog_model.py`, com `contextType: OwnershipContext`, `contextUserLogins`, `CatalogRevision{environments, workflowId/StageId, completeness}`), parse concentrado no adapter (`_translate_row`) e §9 restaurado nas fronteiras. O SATÉLITE desta fatia consome a entry TIPADA (identidade/posse vêm de `ApiCatalogEntry` — nota: `contextType` é `StrEnum`, converter para `str` no `ApiContext.type` do contrato); o DTO de saída permanece projeção mínima. Sinergia FREE: `CatalogRevision.completeness` (objeto aninhado, ver D9) dá à `sen list -r` o teaser por revisão — espelho integral segue território DESTE comando.

**D9.b — Resposta do use-case TIPADA: `CompletenessView` (revisão 28/09).** A regra "dict cru não atravessa fronteiras" vale SIMETRICAMENTE para a borda application→inbound: o `CompletenessService` responde com `CompletenessView` (dataclass frozen em `domain/models/completeness_view.py`, estilo `CatalogRevisionInfo` — SEM envelope pydantic; não revive `SenCompleteness`), e o CLI consome atributos (`view.api.name`, `view.score`), jamais chaves soltas. O ÚNICO dict que nasce é em `view.to_document()`, a serviço do canal stdout (JSON/YAML via `display_output`). Estrutura: `CompletenessApi{manager_id,name,version,context?}` + `CompletenessSuggestion{index,text}`; gate/score são campos da view (o render do CLI deriva deles — inclusive gate deixou de ser constante do CLI).

**D10 — `api_id` no adapter NÃO é obrigatório (revisão 28/09).** O campo existia no construtor do `ManagerApiAdapter` como herança do fluxo legacy (fallback do `get_api_by_id(None)`), mas flujos novos (listing, completeness) o ignoram: virou `api_id: Optional[int] = None`; factories de listing/completeness PARAM de passar (o parâmetro mentia — `settings.API_ID` parecia amarração da consulta); só o bare pipeline legacy segue repassando. Regra da casa: parâmetro só entra onde o consumo exige.

**D9 — A completude mora DENTRO de `CatalogRevision`, como objeto aninhado (pivot de model, 28/09).** Em vez de uma família nova de models (`CompletionReading` side-along), a leitura de completude é representada por `CatalogRevisionCompleteness{score, suggestions[list[str]]}` DEFINIDO EM `catalog_revision_model.py` e ANINHADO como `CatalogRevision.completeness: Optional[CatalogRevisionCompleteness]` — a `CatalogRevision` já acumula as várias faces da revisão, e a ÚNICA novidade que o endpoint trouxe frente ao frame existente é a lista de sugestões (o score de completude já era presenciado no frame, agora co-localizado). O flat `completenessScore` é APOSENTADO (sem manter os dois); o frame do catálogo popula `completeness={score}` (sem suggestions); o endpoint `GET /revisions/{rid}/completeness` popula o MESMO objeto com score + suggestions — um único modelo de domínio, duas fontes, casas coordenadas: o teaser (`sen list -r`) e o espelho integral (`sen completeness`) têm a MESMA forma. **Sem model-envelope separado (decisão de revisão):** o arquivo `completeness_model.py` e o envelope `SenCompleteness` foram EXCLUÍDOS — a leitura de domínio é `CatalogRevision.completeness` aninhado e a resposta de saída é a VIEW TIPADA `CompletenessView` (ver D9.b), cujos constants de contrato (`schema` v1, gate 70) residem no `completeness_service.py`; o dict do contrato nasce apenas em `to_document()` no canal stdout. Nunca dict cru de wire nem model-envelope redundante. Efeito colateral documentado: a spec `api-catalog` recebe MODIFIED mínimo (cenário "Duplicate completeness score ignored" passa a citar `CatalogRevision.completeness.score`); a spec `sen-list` NÃO muda (coluna COMPLETE intacta, derivada de `rev.completeness.score`).

**D5 — Enriquecimento de identidade permanece degradável COMO CHAMADA, e é invisível como contrato (C3/C4 reenquadradas).** Posse/Contexto só existem no api-finder: o lookup (`ManagerApiPort.list_api_detail`, o MESMO ponto do `sen list`) permanece soft-fail (`exit 0`, `managerId` garantido, campos `null` quando falha). **Visibilidade r5 APLICADA também aqui (decisão 28/09):** o `CompletenessService` recebe a `LoginSession` (opcional, igual ao `ApiListingService`) e aplica a MESMA regra de domínio (`finder_row_visible_to` de `catalog_visibility`) ao resultado do lookup — entry invisível degrada IGUAL a lookup falho (identidade cega), nunca erro sintético; a autorização de fato da consulta segue sendo do servidor (403 → exit 2). O service consome o domínio diretamente (sem depender do `ApiListingService`). **Bloco de estado-de-coleta eliminado do contrato** (revisão 25/09): o output exibe dados de completeness + dados da API; ausência fala por si. Connect Catalog também fora (era subsídio da ponte AG). Importante para o smoke: a lookup usa `customSearch=(apiId:X)` do catálogo, que só expõe a API **vigente** do frame — a POSSE exibida é da API, não da revisão consultada (comportamento igual à tela).

**D6 — Aritmética perdida vira design de tela, não invenção de dado.** Com `severity` indisponível, a tabela `Sev │ Impact │ Where` (F1/F5/F7) é aposentada; lista `Suggestions` numerada + word-wrap integral substitui. `--score-only` mantém headline + barra/gate (F6). `-v` permanece só verbosidade. A paleta colorida de classificação (F2) **morre junto**: sem classificação no wire (probe 25/09), o headline exibe apenas o percentual neutro + barra/gate — cores ficam reservadas para quando a plataforma expor bucket/classification (P-f/Q4).

**D7 — Erros (G1 reajustado).** Matriz: ausência de `--api-id`/`--revision` ⇒ `exit 1` pré-rede (A4 mantido); 401/403/404/409/422 e 5xx esgotado do Manager ⇒ `exit 2`; vazios reais/satélite caído ⇒ `exit 0`. Novo cenário específico: revisão inexistente/inatingível (`404` do path) → mensagem PT-BR orientando `sen list api --id X --revisions`. Fim da recusa sintética "revisão antiga" (regra selada dos problemas revogada — qualquer revisão alcançável é respondida).

**D8 — Autenticação e moeda de token (herdado).** O comando requer a sessão válida via `sen login`; jwt plataforma-native (P-b) continua pré-condição de produção. Nada de tokens na saída (G2 padronizado).

## Risks / Trade-offs

- [Perda de granularidade: sem `ruleId/severity/range`] → Mitigado com lista simples de suggestions e gate por headline; granularidade fica documentada como retrocompatibilidade com o AG (tabelas possíveis se/quando fonte AG historizar revisões).
- [`suggestions[]` sem ordenação lógica documentada pelo backend] → Ordem de chegada usada como contrato de exibição (index crescente); automação que reordene faz por conta própria.
- [Duplicidade conceitual com `sen list` (completeness por revision no drill-down)] → Fazendas distintas: lá é teaser por linha (frame do catálogo); aqui é espelho integral por revisão — nenhum requisito novo altera a spec `sen-list`.
- [Pendência P-b (JWT platform-native)] → Bloqueio de produção independente; smokes/documentação assumem sessão válida no ambiente de testes.

## Migration Plan

Sem código legado a migrar (nenhuma impl anterior). Rollout = implementação nova sobre a branch base (`feat/command-sen-completeness`). Rollback trivial (ramo não mergeado). ADR 0008 recebe nota de supersedência parcial (fonte primária); docs de problemas mantidos e anotados.

## Open Questions

- Q1 (para plataforma): `suggestions[]` tem ordem estável/peso associado? Hoje tratamos como string list sem ranking.
- Q2: revisões de APIs do modo revisão (draft/non-deployed) retornam 200 igual? (herda P9/P-b; guardado para smoke.)
- Q3: campo `gate` — deve somir no contrato enquanto P-a não avança? Decidido: permanecer (valor fixo do P10) para estabilidade do contrato v1.
- Q4: classificação (Basic/Intermediate/Advanced) — aguardar a Plataforma expor o bucket no wire (Manager ou AG); enquanto não vier, headline exibe apenas o percentual (derivação client-side rejeitada em D2).
